# Production Mobile Lighthouse and Console Error Check

I rebuilt the app and audited the production preview with Lighthouse 12.8.2 using simulated mobile throttling at 412 × 823. The user's reported Performance score of 73 did not reproduce in the isolated local run. Two fresh production runs scored 100 in all four categories.

The final report names `h1#studio-title` (“Find your rhythm.”) as the LCP element. Its LCP breakdown records about 9 ms to first byte and 514 ms of element render delay. The FCP sub-audit scored 0.98 at 1.3 s.

## Remaining audit estimates

- Lighthouse estimates 42 KiB of unused JavaScript from the 71.8 KiB transferred app bundle.
- The 2.9 KiB production stylesheet is render-blocking, with an estimated 150 ms saving.
- The network dependency tree insight is flagged for the document's JS and CSS requests.
- Unused CSS passes. There are no custom font, audio-file, large-image, or third-party script requests. Audio is generated by Web Audio after user interaction.

These diagnostics did not reduce Performance in either production run. The app already returns 100 in the clean environment, so I made no app code changes or loading changes that could risk initial rendering or audio activation just to suppress score-neutral estimates.

## `gads-scrapper.js` and `onboarding.js`

Neither filename or error text exists in the Lab3_HW source. The production request list contains only the app document, its JS and CSS bundles, and the favicon; it does not request either script. Lighthouse's `errors-in-console` audit passes, and a clean Chrome session recorded no page console errors or requests matching those names while exercising the app.

That evidence rules out these errors being emitted by this React application in the production preview. They are consistent with scripts injected by a browser extension or another browser-side integration. The filenames alone do not identify a specific extension; the exact source URL or extension ID from the user's DevTools stack trace would be needed to name it.
